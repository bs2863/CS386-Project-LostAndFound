## 1. Introduction
### Description:
<!-- Description: Write a focused paragraph describing your system -->
Our (Group 2's) project is a system to allow community members on the
NAU Flagstaff Mountain Campus to search for items that they lost, as well as
allowing those who found it to report its location. Trusted staff have the role
of moderating and editing lost & found item listings as needed, as well as mediating
the return of high-value items to ensure that they are not returned to the wrong
person.

Users interact with the system through a dedicated web interface, logging in with NAU
CAS credentials for identification, authentication, authorization, and accountability.

### Minimum Viable Product (MVP):
<!-- MVP: Describe the main features of the MVP and identify which are implemented in this release -->
The minimum viable product is a web application that shows missing items and filters out the other items as the user inputs information about the item they have lost. Certain users like front desk workers would be able to input missing items and the information and the application would display the item to the students.

This MVP solves the problem of people wasting time trying to find the item. As the user uses the filters to find their item, the amount of items shown decreases until the user finds what they are missing. Then, they can go straight to the lost and found in a building instead of looking around campus.

## 3. Automated Testing
<!-- Objective: Demonstrate a comprehensive automated testing approach. -->

### Testing framework
We use the **Node.js built-in test runner** (`node:test`) with `node:assert`.

For us, this was the simple and obvious choice. We didn't need to include any extra dependencies since the backend already needs a recent version of Node.js for its built-in SQLite module, and the test runner comes with it. Not to mention that extra frameworks would likely also add packages for every team member to install and keep up to date. The test runner gives us test functions, setup and cleanup hooks, and mocking (`mock.method`) to replace the database with a fake when testing route logic on its own, and all tests are easy to run with a single `npm test` command from the project's backend folder.

### Test location
[`backend/tests/`](https://github.com/bs2863/CS386-Project-LostAndFound/tree/main/backend/tests)

| File | Approach | What it covers |
|---|---|---|
| [`items.test.js`](https://github.com/bs2863/CS386-Project-LostAndFound/blob/main/backend/tests/items.test.js) | The database is replaced by a mock | Item routes on their own: listing items, saving a valid item, rejecting an item with missing fields |
| [`api.test.js`](https://github.com/bs2863/CS386-Project-LostAndFound/blob/main/backend/tests/api.test.js) | A real SQLite database held in memory | The SQL itself: category/location endpoints, the type and search filters, category/location names in results, saving items, rejecting unknown categories |

The two approaches complement each other. Mocks keep the route tests fast and focused, while the in-memory database checks that the queries actually return the right rows. `api.test.js` resets its data before every test, so tests do not depend on each other, and the real `lost-and-found.db` file is never touched.

### Test example
- **Test:** "POST item with an unknown category is rejected and not saved" in [`backend/tests/api.test.js`](https://github.com/bs2863/CS386-Project-LostAndFound/blob/main/backend/tests/api.test.js)
- **Source code tested:** The `POST /api/v1/items` handler in [`backend/items.js`](https://github.com/bs2863/CS386-Project-LostAndFound/blob/main/backend/items.js)
- **What it validates:** When an item is submitted with a category id that doesn't exist (`C999`), the API must answer `400 Bad Request` and must not save anything. The test sends the item, checks the status code, and then searches for the item to confirm it is not in the database. This protects the data that future item matching depends on: every saved item has a real category and location.

## 4. Technology Stack

### Frontend:
Our frontend has been developed using plain HTML, CSS, and Javascript, without a framework.
We chose this strategy primarily out of ease, as a more advanced framework was not necessary
for a project with this small of a scope, and learning a new framework would have only
contributed to our overall workload.

### API
Our API is developed in Node.js using Express.js for request handling and middleware. We chose
Node.js as it was something we were all already familiar with, and Express as it had a straightforward
developer experience without compromising speed.

### Database
We chose to use SQLite for our database and database management system. We made this decision to
minimize the number of infrastructure dependencies the project would rely on: SQLite relies only
on a single flat file and the DBMS consists of one library. In contrast, a more advanced or complex
DBMS like Postgres or MySQL would have added at least one external dependency and slowed our response
times by introducing further network latency. SQLite is very widely-deployed, reliable, and its few
limitations are not likely to be pain points during this project.

## 5. Learning Strategy
The team acquired the necessary technical skills by independent study. In the beginning of the project, the team was asked about their skills and knowledge. Most of the team had taken a website programming course. However, most of the team lacked backend programming and database skills. The team used documentation as a learning resource. Node.js has an official reference documentation that the members of the team use. The team could have also used video tutorials if they felt that they needed more support on a topic. The team shared knowledge by sending links to resources to learn about topics in our team's Discord server.

A challenge faced by members where being unsure of how to implement a feature. The team has a dedicated coding discussion channel so teams can share knowledge and support a member. Another challenge faced is that some of the team was unsure how to run the backend. Rose Hankins created a guide so the members can follow if they were unsure how. 

Each member had to do independent study so not each team member spent the same time acquiring skills. However, at the start of the project,the team studied technologies they did not know much about for at least 3 hours.
